### 1.2 架构原则

| # | 原则 | 说明 |
|---|------|------|
| 1 | 领域层纯净 | Domain 层零外部依赖，仅依赖 JDK |
| 2 | 依赖方向内向 | Adapter → App → Domain ← Infrastructure |
| 3 | 限界上下文隔离 | 各上下文独立模块，跨上下文通过 ACL/事件通信 |
| 4 | 单一职责聚合 | 每个聚合根对应一个 Repository，事务边界 = 聚合边界 |
| 5 | 接口契约优先 | 前后端通过 API 契约对接，先定义后实现 |
| 6 | 最小依赖原则 | 不引入消息队列等中间件，用 Spring 事件机制替代 |

### 1.3 架构约束

- 部署目标：单机 Docker Compose，面向毕设答辩演示
- 用户规模：单机构，预期并发 < 50
- 不考虑高可用、负载均衡、分布式部署
- 不引入消息队列，跨聚合通信使用 Spring 事件机制

### 2.2 关键选型决策记录（ADR）

#### ADR-001：MyBatis-Plus vs JPA/Hibernate

**决策**：选择 MyBatis-Plus。

**理由**：
- 国内生态成熟，学习资料丰富
- DOMAIN 中已定义完整 DDL，可直接生成代码
- 复杂查询（FEFO 排队、统计报表）SQL 可控性强
- 毕设场景下调试更直观，SQL 日志可读性好

**替代方案**：JPA/Hibernate — 自动化程度高但复杂 SQL 控制困难，国内毕设生态不如 MyBatis。

#### ADR-002：不引入消息队列

**决策**：使用 Spring `ApplicationEventPublisher` + `@TransactionalEventListener(AFTER_COMMIT)` 替代 MQ。

**理由**：
- 单机部署场景下 MQ 增加运维复杂度但无收益
- 领域事件数量有限（6 条核心事件）
- 同步事件 + 补偿策略足够满足可靠性要求
- DOMAIN 模型中跨聚合通信已按此方式设计

#### ADR-003：Redis 仅用于辅助，不做核心数据依赖

**决策**：Redis 承担辅助角色，核心数据全部存储在 MySQL。

**Redis 职责范围**：
- 短信验证码存储（5 分钟 TTL）— 同时写入 `sms_verification` 表作为审计记录
- JWT Token 黑名单（注销用，TTL = Token 剩余有效期）
- 接种排队实时缓存（可选加速）

**理由**：
- MySQL 8.0 在毕设负载下完全足够
- 避免 Redis 故障导致核心业务不可用
- 降低运维复杂度

#### ADR-004：数据库关键策略

**决策**：MySQL 8.0 采用以下策略（与 DOMAIN 共享内核 §7-§9 保持一致）：

| 策略 | 值 | 说明 |
|------|-----|------|
| 事务隔离级别 | `READ_COMMITTED` | 避免不可重复读对业务的影响，MySQL 8.0 默认 REPEATABLE_READ 需显式修改 |
| 物理外键 | 不使用 | 所有 FK 关系在应用层通过 Repository 校验，避免级联锁和跨上下文耦合 |
| 乐观锁 | `hospital_vaccine_summary.version` | 库存汇总表使用 version 字段乐观锁，防止并发更新丢失 |
| 并发控制 | `SELECT FOR UPDATE` | 库存变更和状态变更操作在事务内使用行锁，固定加锁顺序预防死锁 |

### 3.3 各层职责与依赖规则

| 层 | 职责 | 允许的依赖 | 禁止事项 |
|----|------|-----------|---------|
| **Adapter** | HTTP 路由、参数校验（@Validated）、响应格式化 | App 层、Domain 层（只读查询） | 直接访问 Repository、包含业务逻辑 |
| **Application** | 用例编排、@Transactional 事务管理、DTO 转换、领域事件发布 | Domain 层、Infrastructure 层接口 | 包含业务规则（属于 Domain） |
| **Domain** | 聚合根、实体、值对象、领域服务、领域事件、Repository 接口 | 仅 JDK | 依赖任何外部框架 |
| **Infrastructure** | Repository 实现、MyBatis Mapper、Redis 操作、外部服务 | Domain 层（实现接口） | 直接被 Adapter 层依赖 |

### 3.4 跨上下文通信机制

对应 DOMAIN 领域模型总览中定义的 Context Map：

| 通信模式 | 机制 | 实现位置 | 示例 |
|---------|------|---------|------|
| **Open Host Service** | App 层直接调用目标上下文的 AppService | Application 层 | 所有上下文调用 Identity 做鉴权 |
| **领域事件** | Spring Event + `@TransactionalEventListener(AFTER_COMMIT)` | Adapter 层事件监听器 | 预约完成 → 留观创建记录；接种完成 → 预约状态更新 |
| **ACL（防腐层）** | Infrastructure 层封装对其他上下文 Repository 的直接调用 | Infrastructure 层 | 登记上下文调用库存上下文锁定批次（FEFO） |

**事件通信矩阵**（来源：DOMAIN-OVERVIEW-001）：

| 事件 | 发布方 | 订阅方 | 触发时机 |
|------|-------|-------|---------|
| AppointmentSignedIn | Appointment | Register | 签到完成（T3） |
| AppointmentCancelled | Appointment | Stock | 预约取消（T2） |
| VaccinationExecuted | Vaccinate | Observe | 接种执行（T6） |
| ObservationFinished | Observe | Appointment | 留观结束（T7） |

### 3.5 数据访问策略（Repository 实现规范）

**核心规则**：

1. Domain 层只定义接口（如 `UserRepository`），不包含任何实现细节
2. Infrastructure 层通过 MyBatis-Plus 实现 Repository 接口
3. PO（持久化对象）与聚合根完全分离，通过 Converter 双向转换
4. 每个 RepositoryImpl 对应一个 Mapper 接口
5. 简单 CRUD 使用 MyBatis-Plus 内置方法
6. 复杂查询（FEFO 批次锁定、统计报表）使用 MyBatis XML 自定义 SQL
7. 禁止在 Domain 层暴露 PO 或 Mapper

### 3.6 定时任务设计

系统使用 Spring `@Scheduled` 注解实现定时任务，覆盖以下场景：

| 任务 | Cron 表达式 | 触发上下文 | 说明 |
|------|------------|-----------|------|
| 预约过期扫描 | `0 30 0 * * ?`（每天 00:30） | Appointment | 将已过预约日期且 status=1 的预约标记为 status=4（已过期） |
| 批次临期/过期扫描 | 固定间隔（60 分钟） | Stock | 扫描 `vaccine_batch` 表，临期标记 status=1，过期标记 status=2 |
| 库存预警扫描 | 固定间隔（60 分钟） | Stock | 检查可用库存低于预警阈值的疫苗，生成 `stock_alert_log` 记录 |
| 库存汇总补偿 | 固定间隔（5 分钟） | Stock | 对比批次明细与汇总表，修正不一致数据 |
| 留观超时兜底 | 固定间隔（10 分钟） | Observe | 超过 60 分钟未结束的留观自动完成，防止遗漏 |

**对象转换链路**：

```
Controller 层          Application 层          Infrastructure 层         数据库
    │                      │                         │                     │
    │  DTO (请求)          │                         │                     │
    │─────Assembler──────▶ │  Aggregate              │                     │
    │                      │─────Repository 接口──▶ │                     │
    │                      │                         │──Converter──▶ PO──▶ │ SQL
    │                      │                         │◀──Converter── PO ◀─ │ Result
    │                      │◀──Repository 返回──── │                     │
    │  DTO (响应)          │  Aggregate              │                     │
    │◀────Assembler─────── │                         │                     │
```

### 4.4 前后端接口对接规范

| 项目 | 规范 |
|------|------|
| Base URL | `/api/v1`，如 `/api/v1/appointments` |
| 认证方式 | `Authorization: Bearer <jwt_token>` |
| 请求格式 | `Content-Type: application/json` |
| 响应格式 | `{ code: 200, message: "success", data: {...}, timestamp: 1700000000000 }` |
| 错误响应 | `{ code: 40001, message: "预约已过期", data: null, timestamp: ... }` |
| 分页请求 | `GET /api/v1/appointments?page=1&size=20` |
| 分页响应 | `{ data: { records: [], total: 100, page: 1, size: 20, pages: 5 } }` |
| 错误码 | 复用 DOMAIN 共享内核中已定义的错误码体系（DOMAIN-CROSS-CUTTING-001） |
| Token 刷新 | 单 Token + 滑动过期（访问时续期），过期返回 1001 跳转登录 |

**统一请求封装（api/request.js）职责**：

1. 请求拦截：自动注入 Token、设置 Content-Type
2. 响应拦截：code === 200 放行，非 200 统一弹 Toast 提示
3. 1001 处理：清除 Token、跳转登录页
4. 网络异常兜底：Toast "网络异常，请稍后重试"
5. Loading 控制：按需显示/隐藏 loading 动画

## 5. 安全架构

### 5.1 认证流程（JWT）

```
登录请求 → IdentityController.login(phone, password)
    │
    ▼
IdentityAppService 验证密码（BCrypt 比对）
    │
    ▼
AuthDomainService 验证通过 → 签发 JWT
    │
    ├── payload: { userId, phone, roles: ["USER"], exp: 24h }
    ├── signature: HMAC-SHA256 (服务端密钥)
    └── 返回 Token 给前端
    │
    ▼
前端存储 Token → uni.setStorageSync('token', jwt)
    │
    ▼
后续请求 → Authorization: Bearer <token>
    │
    ▼
JwtAuthenticationFilter (OncePerRequestFilter)
    ├── 解析 Token → 获取 userId + roles
    ├── 注入 SecurityContext
    └── 放行至 Controller

注销 → Token 加入 Redis 黑名单 (TTL = Token 剩余有效期)
```

### 5.2 鉴权模型（两层）

| 层级 | 机制 | 说明 |
|------|------|------|
| 功能权限 | RBAC | 用户 → 角色 → 权限码，对应 DOMAIN 中 10 个预设角色 + 权限码体系 |
| 数据权限 | Repository 过滤 | 医生只能查看本院/本窗口数据，监护人只能查看自己儿童的数据，管理员按院区过滤 |

**功能权限实现**：

```
Controller 层注解鉴权：
@PreAuthorize("hasAuthority('appointment:create')")  ← 对应 DOMAIN 共享内核权限码

执行链路：
请求 → JwtFilter(认证) → PermissionInterceptor(鉴权)
    → 从 SecurityContext 取 roles → 查询角色对应的权限码集合
    → 与 @PreAuthorize 注解比对 → 通过/拒绝(403)
```

**数据权限实现**：

```
Repository 层过滤（MyBatis-Plus DataPermissionInterceptor）：

Doctor 操作 → 自动拼接 WHERE hospital_id = #{currentHospitalId}
Guardian 操作 → 自动拼接 WHERE child_id IN (#{userChildIds})
Admin 操作 → 根据管理范围拼接院区条件

实现方式：
    ThreadLocal 存储当前用户上下文
    → MyBatis-Plus 拦截器在 SQL 执行前自动追加数据过滤条件
```

### 5.3 接口安全策略

| 措施 | 实现方式 |
|------|---------|
| HTTPS | Nginx 配置 SSL 证书，强制 HTTPS 跳转 |
| 参数校验 | Jakarta Validation（@NotBlank、@Pattern、@Size 等），Controller 层 @Validated 触发 |
| 防重放 | 关键写操作（接种、库存扣减）要求前端传 requestId（UUID），Redis 去重，5 秒内相同 ID 拒绝 |
| SQL 注入防护 | MyBatis-Plus 参数化查询 + XML 中 `#{}` 绑定，禁止 `${}` |
| XSS 防护 | 全局 XSS 过滤器，请求参数中 HTML 标签转义 |
| 敏感数据脱敏 | 响应中手机号中间 4 位掩码（138\*\*\*\*1234），身份证号掩码 |
| 接口限流 | Guava RateLimiter，短信发送接口 60 秒/次，登录接口 5 次/分钟 |
| 日志审计 | 关键操作（接种、库存变动、角色变更）记录操作日志（操作人、时间、IP、操作内容） |

## 7. 附录

### 7.1 技术选型对比矩阵

#### ORM 框架对比

| 维度 | MyBatis-Plus | JPA/Hibernate |
|------|-------------|---------------|
| SQL 控制度 | 高，完全可控 | 低，自动生成为主 |
| 学习曲线 | 中等，需熟悉 SQL | 较高，需理解 JPA 机制 |
| 复杂查询支持 | 原生 SQL + XML | Criteria API / @Query |
| 代码生成 | 内置 Generator | 内置 |
| 国内生态 | 丰富 | 一般 |
| 调试便利 | SQL 日志直观 | 需要统计日志 |
| **结论** | **选用** | 不选用 |

#### 缓存方案对比

| 维度 | Redis（选用） | Caffeine（本地缓存） | 无缓存 |
|------|-------------|---------------------|-------|
| 分布式支持 | 是 | 否 | — |
| 验证码存储 | 天然 TTL | 需自己实现 | 无法实现 |
| Token 黑名单 | Set + TTL | 需自己实现 | 无法实现 |
| 运维复杂度 | 中等（Docker 容器） | 无 | 无 |
| **结论** | **选用** | 不选用 | 不选用 |
