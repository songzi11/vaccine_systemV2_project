## 2. 评审体系

### 2.1 三大支柱、10个维度、100分

| 支柱 | 权重 | 维度 | 分值 | 说明 |
|------|------|------|------|------|
| **支柱一：PRD符合性** | **35分** | D1: PRD功能覆盖 | 12 | 前端页面是否覆盖PRD定义的全部功能点 |
| | | D2: 页面流程覆盖 | 12 | PRD业务流程是否在页面跳转中完整体现 |
| | | D3: 业务规则覆盖 | 11 | PRD输入校验、状态约束是否在前端交互中体现 |
| **支柱二：架构一致性** | **35分** | D4: 技术选型一致性 | 8 | 技术栈是否与架构设计§2/§4一致 |
| | | D5: API接口一致性 | 10 | 前端调用的API是否与API接口设计文档对齐 |
| | | D6: 安全方案一致性 | 9 | JWT/权限/错误处理是否与架构设计§5一致 |
| | | D7: 数据模型一致性 | 8 | 状态码/枚举值/Store字段是否与后端对齐 |
| **支柱三：设计完备性** | **30分** | D8: 路由与页面完备性 | 8 | 路由定义、页面覆盖、两端共存是否无冲突 |
| | | D9: 组件与交互完备性 | 8 | 可复用组件、核心页面交互描述是否充分 |
| | | D10: 异常处理完备性 | 7 | 错误码映射、网络异常、边界场景是否覆盖 |
| | | D11: 状态管理与轮询完备性 | 7 | Store设计、轮询策略、生命周期管理是否合理 |

### 2.2 一票否决项

以下任一项触发，对应支柱直接计 0 分：

| 编号 | 否决项 | 适用支柱 |
|------|-------|---------|
| V1 | PRD定义的核心功能点在前端设计中完全缺失（如签到/接种等核心操作无对应页面） | 支柱一 |
| V2 | 核心业务流程（预约→签到→预检→登记→接种→留观）在前端页面流中存在断裂步骤 | 支柱一 |
| V3 | 前端调用的API端点与API接口设计文档存在路径或HTTP方法矛盾 | 支柱二 |
| V4 | 认证流程或权限控制方案与架构设计§5矛盾 | 支柱二 |
| V5 | 枚举值/状态码/错误码与共享内核定义存在矛盾 | 支柱二 |

### 2.3 评分等级

| 等级 | 分数范围 | 说明 |
|------|---------|------|
| S | 95-100 | 优秀，可直接进入开发 |
| A | 85-94 | 良好，少量优化后可进入开发 |
| B | 75-84 | 合格，需要修复中等问题 |
| C | 60-74 | 不合格，需要重大修复 |
| D | < 60 | 严重不合格，需要重写 |

### D2: 页面流程覆盖（12分）

**检查方法**：追踪核心业务流程在两端页面间的跳转链路，验证每个环节是否有对应页面且跳转路径完整。

#### 核心流程链路

| 核心流程 | 医生端页面链路 | 家长端页面链路 |
|---------|-------------|-------------|
| 预约全流程 | — | 创建预约→预约列表→预约详情→流程指引 |
| 签到→预检 | 签到队列→签到确认→预检队列→预检评估 | 预约详情→流程指引（显示当前步骤） |
| 登记+叫号 | 登记队列→登记处理→叫号面板→确认到达 | 流程指引（显示排队状态） |
| 接种 | 接种队列→接种执行→接种成功→留观提醒 | 流程指引（显示接种完成） |
| 留观 | 留观队列→留观详情→留观结束 / 不良反应上报 | 流程指引（显示留观状态） |
| 库存管理 | 库存总览→批次列表→批次详情→调拨/销毁 | 疫苗目录浏览 |

#### 检查项

| 检查项 | 说明 |
|--------|------|
| 每个流程环节有对应页面 | 链路中每个步骤都有独立页面 |
| 页面间跳转方向正确 | 正向流程和逆向返回都有描述 |
| 流程分支有覆盖 | 如预检不通过、叫号过号、异常留观等分支路径 |
| 家长端流程指引完整 | 流程指引页能展示当前步骤和后续步骤 |

#### 扣分规则

- 每个断裂的流程环节（缺少对应页面）：**-2分**
- 每个缺少返回路径的页面：**-0.5分**
- 每个未覆盖的流程分支：**-1分**

### D6: 安全方案一致性（9分）

**检查方法**：比对系统架构设计§5中的安全方案与前端设计文档中的实现描述。

| 检查项 | 架构设计§5规定 | 前端设计体现 |
|--------|-----------|-------------|
| JWT Token存储 | uni.setStorageSync('token', jwt) | request.js中Token读取和注入 |
| Token自动注入 | 请求拦截器注入 `Authorization: Bearer <token>` | request.js请求拦截器描述 |
| Token过期处理 | code=1001 → 清除Token → 跳转登录 | 响应拦截器处理描述 |
| 注销流程 | Token加入Redis黑名单 + 清除前端状态 | logout()实现描述 |
| 防重放机制 | 写操作传X-Request-Id（UUID v4），Redis去重 | request.js写操作自动生成 |
| 角色路由守卫 | 登录后按roles跳转不同首页 | 登录成功后角色判断+跳转逻辑 |
| 动态TabBar权限 | 按角色显示不同Tab | CustomTabBar组件+Pinia角色判断 |
| 按钮级权限控制 | @PreAuthorize对应的前端按钮显隐 | 页面中权限相关按钮的条件渲染 |
| 敏感数据脱敏 | 手机号掩码(138\*\*\*\*1234)、身份证掩码 | 个人中心页展示逻辑 |

#### 扣分规则

- 每项安全机制未在前端设计中体现：**-1分**

---

### D7: 数据模型一致性（8分）

**检查方法**：比对前端设计中的状态码映射、枚举值、Store字段与后端共享内核/数据库设计。

| 检查项 | 说明 |
|--------|------|
| 预约状态码映射 | 前端状态颜色映射表中的状态码（1/2/3/4/6/7/8/9/10）与共享内核状态机一致 |
| 排队项状态码 | 医生端排队项状态（待叫号/已叫号/已到达/已过号/已完成）与后端定义一致 |
| 批次状态码 | 前端批次状态（正常/即将过期/已过期/已销毁）与数据库设计一致 |
| 角色编码 | 前端角色判断使用的编码（USER/DOCTOR_SIGNIN等）与共享内核权限码一致 |
| 疫苗类型枚举 | 一类/二类疫苗分类与数据库设计一致 |
| 不良反应枚举 | 反应类型（局部/过敏/发热/其他）、严重程度（轻/中/重）与PRD/数据库一致 |
| Store字段可映射 | Pinia Store中的state字段可从API响应DTO直接映射或简单组装 |
| 列表展示字段 | 页面展示的字段可从API响应DTO获取（如childName、vaccineName等） |

#### 扣分规则

- 每个状态码或枚举值与后端定义矛盾：**-1分**
- 每个无法从后端DTO映射的前端字段：**-0.5分**

---

### D8: 路由与页面完备性（8分）

**检查方法**：检查前端设计文档中的路由设计是否完整，两端页面共存无冲突。

| 检查项 | 说明 |
|--------|------|
| TabBar页面全部定义 | pages.json中TabBar配置完整列出 |
| 非Tab页面全部注册 | 所有跳转目标页面在路由设计中列出 |
| 页面无孤立 | 每个页面至少有一个入口可达（Tab/列表跳转/快捷入口） |
| 两端路由无冲突 | 医生端(`pages/doctor/*`或`pages/queue/*`等)和家长端(`pages/guardian/*`或`pages/appointment/*`等)路由前缀不冲突 |
| 公共页面复用 | 登录页等公共页面两端共用，无重复定义 |
| 页面路径格式统一 | 路径命名风格一致（kebab-case） |

#### 扣分规则

- 每个缺失的路由定义：**-0.5分**
- 每个孤立页面（无入口可达）：**-0.3分**
- 两端路由冲突：**-2分/处**

---

### D9: 组件与交互完备性（8分）

**检查方法**：检查可复用组件清单和核心页面交互描述的充分程度。

| 检查项 | 说明 |
|--------|------|
| 可复用组件清单完整 | 列出所有设计的可复用组件，注明组件用途和使用页面 |
| 核心页面有交互描述 | 每个核心操作页面（队列/处理/确认等）有详细的UI元素布局描述 |
| 表单校验规则有描述 | 输入框的校验规则（必填/格式/范围/联动）有明确说明 |
| 列表交互有描述 | 下拉刷新、上拉加载更多、搜索、筛选的交互方式有描述 |
| 状态展示有描述 | 加载态、空状态、错误态的展示方式有描述 |
| 操作反馈有描述 | 成功Toast、失败Toast、确认弹窗的触发条件有描述 |

#### 扣分规则

- 每个缺少交互描述的核心页面：**-0.5分**
- 每个缺少校验规则描述的关键表单：**-0.3分**

---

### D10: 异常处理完备性（7分）

**检查方法**：检查前端设计中的错误处理覆盖范围。

| 检查项 | 说明 |
|--------|------|
| 错误码映射表 | 关键业务错误码与前端处理方式（Toast/跳转/弹窗）有对应关系表 |
| 网络异常处理 | 请求超时、断网场景有兜底提示和重试机制 |
| 空状态处理 | 列表为空、无数据、无搜索结果有占位展示 |
| 边界场景 | 并发操作（如同时叫号）、重复提交、权限不足有处理描述 |
| Token异常处理 | Token过期(1001)、无效(1001)、无权限(1002)的处理链路 |
| 404/页面不存在 | 无效路由的兜底处理 |

#### 扣分规则

- 每种异常场景未覆盖：**-1分**

---

### D11: 状态管理与轮询完备性（7分）

**检查方法**：检查Pinia Store设计和轮询策略的合理性。

| 检查项 | 说明 |
|--------|------|
| Store职责清晰 | 每个Store的state/getters/actions有明确职责，无冗余 |
| 轮询间隔合理 | 各页面的轮询间隔与业务时效性需求匹配 |
| 轮询生命周期管理 | onShow启动、onHide/onUnload停止，无内存泄漏风险 |
| 轮询冲突处理 | 页面切换时旧轮询正确清理，新轮询正确启动 |
| 数据刷新策略 | 下拉刷新、手动刷新、自动轮询的触发场景清晰 |
| Store持久化 | 需要持久化的数据（如token、用户信息）有持久化方案 |
| 跨页面状态共享 | 需要跨页面共享的状态（如排队信息）通过Store管理 |

#### 扣分规则

- 每个Store设计缺陷（职责不清/冗余状态）：**-0.5分**
- 每个不合理的轮询策略（间隔不当/无清理）：**-1分**

## 4. 评审执行步骤

### Step 1: 自动化扫描（约 20 分钟）

扩展现有 `docs/tools/verify_consistency/` 工具，新增检查器：

| 检查器 | 输入 | 输出 |
|--------|------|------|
| `prd_frontend_checker.py` | PRD功能点 + 前端设计文档 | 功能覆盖矩阵 |
| `api_frontend_checker.py` | API接口设计 + 前端api/定义 | 端点路径/方法/参数差异列表 |
| `enum_checker.py` | 共享内核枚举 + 前端状态映射 | 枚举值差异列表 |

### Step 2: 人工评审（约 2 小时）

按维度逐项评审，填写评审表：

```
维度 | 满分 | 得分 | 问题列表
D1   | 12   |  ?   | P0: xxx, P1: xxx
D2   | 12   |  ?   |
...
```

问题优先级定义（与REVIEW-PLAN-001一致）：

| 级别 | 说明 | 处理要求 |
|------|------|---------|
| P0 | 事实错误（API路径不匹配、状态码矛盾） | 必须修复 |
| P1 | 遗漏（缺少页面、缺少校验规则、缺少错误处理） | 必须修复 |
| P2 | 不一致（文档间描述矛盾、UI组件库不统一） | 应当修复 |
| P3 | 优化建议（轮询间隔调整、组件抽象改进） | 可选修复 |

### Step 3: 修复（约 1-2 小时）

按 P0 → P1 → P2 → P3 优先级修复前端设计文档。

### Step 4: 复审（约 30 分钟）

验证修复是否正确，确认无引入新问题。

### Step 5: 出具评审报告

```
docs/superpowers/specs/前端设计文档评审报告.md
```

报告结构：
1. 评分总览（10维度得分表 + 三支柱汇总）
2. 一票否决项检查结果
3. 各维度详细评审结果（问题列表 + 修复确认）
4. 版本变更记录
5. 最终结论

---

| 条件 | 要求 |
|------|------|
| 无一票否决项 | V1-V5 全部未触发 |
