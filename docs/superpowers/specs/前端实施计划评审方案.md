## 2. 评审体系

### 2.1 四维质量模型、100分制

| 维度 | 权重 | 核心关注 |
|------|------|---------|
| **D1: 设计覆盖度** | **30分** | 实施计划是否完整覆盖设计文档的全部交付物（页面/组件/API/Store/Hooks/路由/样式） |
| **D2: 计划可执行性** | **30分** | 任务拆分粒度是否合理、代码示例是否完整可执行、步骤是否无歧义 |
| **D3: 架构一致性** | **25分** | 技术栈、API路径、数据模型、状态管理是否与架构设计和前端设计文档对齐 |
| **D4: 质量保障** | **15分** | Phase依赖是否合理、边界场景是否覆盖、任务间是否有验证标准 |

### 2.2 一票否决项

以下任一项触发，对应维度直接计 0 分：

| 编号 | 否决项 | 适用维度 |
|------|--------|---------|
| V1 | 设计文档中定义的核心业务页面在实施计划中完全无对应Task。核心页面指：签到确认、预检评估、登记处理、接种执行、留观详情、创建预约、登录页（任一缺失即触发） | D1 |
| V2 | 核心业务流程（预约→签到→预检→登记→接种→留观）在实施计划的Phase编排中存在断裂步骤（某环节无任务覆盖） | D1 |
| V3 | 实施计划中的API路径或HTTP方法与API接口设计文档存在系统性矛盾（非个别遗漏，而是结构性错误） | D3 |
| V4 | 实施计划的技术栈或核心架构方案与系统架构设计文档矛盾（如框架/状态管理/UI组件库不一致） | D3 |
| V5 | 实施计划的依赖关系存在循环依赖或关键前置条件缺失，导致计划无法按序执行 | D4 |

### 2.3 评分等级

| 等级 | 分数范围 | 说明 |
|------|---------|------|
| S | 95-100 | 优秀，可直接进入实施 |
| A | 85-94 | 良好，少量优化后可进入实施 |
| B | 75-84 | 合格，需要修复中等问题 |
| C | 60-74 | 不合格，需要重大修复 |
| D | < 60 | 严重不合格，需要重写 |

## 3. 各维度评审细则

### D1: 设计覆盖度（30分）

**检查方法**：逐一比对前端设计文档中的交付物清单与实施计划的Task列表，验证每个设计交付物是否有对应实施任务。

#### D1.1: 页面覆盖（12分）

**检查方法**：比对设计文档的页面清单与实施计划的Task列表。

| 检查项 | 说明 |
|--------|------|
| 设计文档中每个页面有对应Task | 页面文件路径在设计文档和实施计划中一致 |
| Task的Files部分明确列出页面文件 | 如 `Create: pages/queue/signin.vue` |
| 页面路径格式与设计文档一致 | kebab-case 命名、目录层级与设计文档路由表一致 |

**扣分规则：**
- 每个设计文档有但实施计划无对应Task的页面：**-1分**
- 每个路径不一致的页面文件：**-0.3分**

#### D1.2: 组件覆盖（5分）

**检查方法**：比对设计文档的可复用组件清单与实施计划。

| 检查项 | 说明 |
|--------|------|
| 设计文档中每个可复用组件有对应Task | 组件文件路径一致 |
| 组件Props/Events在代码示例中有体现 | 代码示例展示了组件的使用方式 |

**扣分规则：**
- 每个缺少对应Task的组件：**-0.5分**

#### D1.3: API模块覆盖（5分）

**检查方法**：比对设计文档的API层设计与实施计划的API模块Task。

| 检查项 | 说明 |
|--------|------|
| 设计文档中每个 api/*.js 模块有对应Task | API文件路径一致 |
| 每个API端点函数有代码示例 | 代码示例中包含完整的函数签名（路径/方法/参数） |
| 函数签名与设计文档API清单一致 | 函数名、URL路径、HTTP方法与设计文档对齐 |

**扣分规则：**
- 每个缺少对应Task的API模块：**-0.5分**
- 每个缺少代码示例的API端点函数：**-0.2分**
- 每个函数签名与设计文档不一致的端点：**-0.3分**

#### D1.4: Store/Hooks覆盖（4分）

**检查方法**：比对设计文档的Pinia Store和Hooks清单与实施计划。

| 检查项 | 说明 |
|--------|------|
| 设计文档中每个Store有对应Task | Store文件路径一致 |
| 设计文档中每个Hook有对应Task | Hook文件路径一致 |
| Store的state/getters/actions在代码示例中有体现 | 代码示例展示Store的核心结构 |

**扣分规则：**
- 每个缺少对应Task的Store或Hook：**-0.5分**

#### D1.5: 路由/配置覆盖（4分）

**检查方法**：检查pages.json路由注册、TabBar配置、SCSS变量等配置项是否在实施计划中有对应Task。

| 检查项 | 说明 |
|--------|------|
| pages.json路由注册有对应Task | 设计文档中列出的全部路由在实施计划中注册 |
| TabBar配置有对应Task | 原生TabBar或CustomTabBar的配置有对应代码示例 |
| SCSS设计令牌有对应Task | 颜色/间距/字体等设计变量在uni.scss代码示例中有定义 |

**扣分规则：**
- 每个缺少的路由/配置Task：**-0.3分**

---

### D2: 计划可执行性（30分）

**检查方法**：从执行者视角评估实施计划是否可以直接按Step执行，无需额外补充信息。

#### D2.1: 任务拆分粒度（8分）

| 检查项 | 说明 |
|--------|------|
| 每个Task单一职责 | 一个Task聚焦一个功能单元（一个API模块、一个页面、一个组件等） |
| Task大小合理 | 不存在"一次性实现10+个页面"的巨型Task |
| Step粒度可操作 | 每个Step是一个明确的原子操作（创建一个文件、修改一个配置等） |
| 子任务编排有序 | 同一Task内的Steps按逻辑顺序排列（先依赖后使用） |

**扣分规则：**
- 每个拆分过粗的Task（含3+不相关文件且无子Step分解）：**-1分**
- 每个拆分过细的Task（仅一行import语句级别）：**-0.2分**
- 每个Step顺序颠倒导致执行困难的Task：**-0.5分**

#### D2.2: 代码示例完整度（10分）

| 检查项 | 说明 |
|--------|------|
| 关键文件有完整代码示例 | API模块、Store、核心页面、公共组件有完整可执行的代码 |
| 代码示例可直接使用 | 代码无占位符（如 `// TODO`、`// ...其余逻辑`），复制即可运行 |
| 代码示例使用正确语法 | Vue 3 Composition API (`<script setup>`)、Pinia、uni-app API使用正确 |
| 样式代码有示例 | 核心页面和组件有 `<style>` 部分的SCSS代码 |

**扣分规则：**
- 每个缺少代码示例的关键文件（API/Store/核心页面/公共组件）：**-1分**
- 每个含未完成占位符的代码示例（`// TODO`、`// ...`）：**-0.5分**
- 每处语法错误的代码示例：**-0.3分**
- 每个缺少样式代码的核心页面或组件：**-0.3分**

#### D2.3: 步骤无歧义（7分）

| 检查项 | 说明 |
|--------|------|
| 每个Step有明确操作指令 | 不含"适当处理"、"根据需要"等模糊表述 |
| 文件操作指令清晰 | 创建/修改/删除操作明确，删除操作有安全提示 |
| 依赖引用路径明确 | import路径使用 `@/` 别名，路径无歧义 |
| Step间无跳转 | 不存在"参见其他Task"的跳转引用（每Step自包含） |

**扣分规则：**
- 每个含模糊描述的Step：**-0.5分**
- 每个依赖路径不明确的Step：**-0.3分**

#### D2.4: 文件路径明确（5分）

| 检查项 | 说明 |
|--------|------|
| 每个Task的Files部分完整 | Create/Modify/Delete操作明确标注 |
| 文件路径使用项目相对路径 | 如 `utils/request.js` 而非绝对路径 |
| 文件路径与设计文档一致 | 实施计划中的文件路径与设计文档规划的目录结构一致 |

**扣分规则：**
- 每个未列出文件路径的Task：**-0.5分**
- 每个路径与设计文档不一致的文件：**-0.3分**

---

### D3: 架构一致性（25分）

**检查方法**：将实施计划中的代码示例与架构设计文档、API接口设计文档、共享内核进行逐项比对。

#### D3.1: 技术栈一致性（6分）

| 检查项 | 说明 |
|--------|------|
| 框架使用正确 | 代码示例使用 uni-app + Vue 3 Composition API (`<script setup>`) |
| 状态管理正确 | 使用 Pinia（非 Vuex），代码示例中 `defineStore` 语法正确 |
| UI组件库正确 | 使用 uni-ui 组件（非 uView），组件标签名正确（如 `uni-easyinput`） |
| HTTP请求方式正确 | 使用封装后的 `get/post/put/del` 方法（来自 `utils/request.js`） |
| 样式方案正确 | 使用 SCSS，引用 `uni.scss` 中的设计令牌变量 |

**扣分规则：**
- 每项技术栈使用与架构设计不一致：**-1分**

#### D3.2: API路径一致性（8分）

**检查方法**：逐一比对实施计划代码示例中的API调用与API接口设计文档。

| 检查项 | 说明 |
|--------|------|
| API路径一致 | 代码示例中的URL路径与API设计完全一致（含 `/api/v1` 前缀） |
| HTTP方法一致 | GET/POST/PUT/DELETE与API设计一致 |
| 请求参数一致 | 代码示例中传递的参数名和类型与API设计请求DTO一致 |
| 分页参数一致 | 使用 `page/size` 参数，与API设计一致 |
| 认证Header | 需认证的接口通过 request.js 拦截器自动注入，无需手动传Token |

**扣分规则：**
- 每个API路径不一致：**-0.5分**
- 每个HTTP方法不一致：**-0.5分**
- 每个请求参数名不一致：**-0.3分**
- 每个API设计中有但实施计划未覆盖的端点（该端范围内）：**-0.3分**

#### D3.3: 数据模型一致性（6分）

**检查方法**：比对实施计划代码示例中的状态码、枚举值、Store字段与共享内核/数据库设计。

| 检查项 | 说明 |
|--------|------|
| 状态码映射正确 | Store/组件中的状态码与共享内核状态机一致（如预约状态1/2/3/.../10） |
| 枚举值正确 | 疫苗类型（CLASS_I/CLASS_II）、不良反应类型、严重程度等与后端一致 |
| 错误码正确 | 代码示例中引用的错误码与共享内核错误码体系一致 |
| Store字段可映射 | Store中的state字段可从API响应DTO直接映射或简单组装 |

**扣分规则：**
- 每个状态码或枚举值与后端定义矛盾：**-0.5分**
- 每个错误码与共享内核不一致：**-0.5分**
- 每个无法从后端DTO映射的Store字段：**-0.3分**

#### D3.4: 安全方案一致性（5分）

| 检查项 | 说明 |
|--------|------|
| Token存储方式正确 | 使用 `uni.getStorageSync('token')` / `uni.setStorageSync('token', jwt)` |
| Token自动注入 | 通过 request.js 拦截器自动注入 `Authorization: Bearer <token>` |
| Token过期处理 | code=1001时清除Token并跳转登录页 |
| 防重放机制 | 写操作生成 X-Request-Id（UUID v4） |
| 角色路由守卫 | 登录后按角色跳转不同首页 |

**扣分规则：**
- 每项安全机制未在代码示例中体现：**-0.5分**

### D4: 质量保障（15分）

**检查方法**：从工程管理视角评估实施计划的依赖编排、边界覆盖和验证标准。

#### D4.1: Phase依赖合理性（5分）

| 检查项 | 说明 |
|--------|------|
| Phase间依赖关系正确 | 后续Phase确实依赖前置Phase的产出 |
| 无循环依赖 | 不存在Phase A依赖Phase B，Phase B又依赖Phase A的情况 |
| 前置条件声明完整 | 每份实施计划的"前置条件"部分准确列出所需的基础设施 |
| 跨计划依赖明确 | 如医生端依赖共享基础设施，依赖声明清晰 |

**扣分规则：**
- 每处循环依赖：**-2分**
- 每处错误的前置条件（声明依赖但实际不需要，或需要但未声明）：**-1分**

#### D4.2: 边界场景覆盖（5分）

| 检查项 | 说明 |
|--------|------|
| 空状态处理有对应任务 | 列表为空、无搜索结果等空状态有实施覆盖 |
| 错误处理有对应任务 | 网络异常、Token过期、权限不足等有实施覆盖 |
| 加载状态有对应任务 | 页面加载态（骨架屏/Loading）有实施覆盖 |
| 设计文档中的业务边界有覆盖 | 如叫号超时、过号上限、留观最短时间等 |

**扣分规则：**
- 每个设计文档中有但实施计划未覆盖的边界场景：**-0.5分**

#### D4.3: 验证标准（5分）

| 检查项 | 说明 |
|--------|------|
| 每个Phase有明确的完成标准 | Phase完成后应产出的文件和可验证的功能点 |
| Task的checkbox可验证 | 每个Step可通过文件是否存在、代码是否可编译等方式验证 |
| 整体计划有验收标准 | 计划开头或结尾有明确的完成条件和验收清单 |

**扣分规则：**
- 每个缺少验证标准的Phase：**-1分**
- 整体计划无验收标准：**-1分**

## 4. 评审执行步骤

### Step 1: 自动化扫描（约 15 分钟）

扩展现有 `docs/tools/verify_consistency/` 工具，新增检查器：

| 检查器 | 输入 | 输出 |
|--------|------|------|
| `design_plan_coverage_checker.py` | 前端设计文档（页面/组件/API/Store/Hooks清单） + 实施计划（Task列表） | 覆盖矩阵：每个设计交付物是否有对应实施Task |
| `plan_api_checker.py` | API接口设计文档 + 实施计划代码示例中的API调用 | API路径/方法/参数差异列表 |
| `plan_enum_checker.py` | 共享内核枚举 + 实施计划代码示例中的状态码/枚举值 | 枚举值差异列表 |

### Step 2: 人工评审（约 2 小时）

按维度逐项评审4份实施计划，填写评审表：

```
计划名称 | 维度 | 满分 | 得分 | 问题列表
共享基础设施 | D1   | 30   |  ?   | P0: xxx, P1: xxx
共享基础设施 | D2   | 30   |  ?   |
...
家长端     | D1   | 30   |  ?   |
...
医生端     | D1   | 30   |  ?   |
...
管理员端   | D1   | 30   |  ?   |
...
```

问题优先级定义：

| 级别 | 说明 | 处理要求 |
|------|------|---------|
| P0 | 事实错误（API路径不匹配、状态码矛盾、依赖断裂） | 必须修复 |
| P1 | 遗漏（缺少Task、缺少代码示例、缺少边界场景覆盖） | 必须修复 |
| P2 | 不一致（文件路径不统一、代码示例语法问题） | 应当修复 |
| P3 | 优化建议（任务拆分优化、代码示例改进） | 可选修复 |

### Step 3: 修复（约 1-2 小时）

按 P0 → P1 → P2 → P3 优先级修复实施计划。

### Step 4: 复审（约 30 分钟）

验证修复是否正确，确认无引入新问题。

### Step 5: 出具评审报告

```
docs/superpowers/specs/前端实施计划评审报告.md
```

报告结构：
1. 评分总览（4份计划 × 4维度得分表）
2. 一票否决项检查结果
3. 各维度详细评审结果（按计划分列，问题列表 + 修复确认）
4. 修复确认记录
5. 复审结果
6. 最终结论

---

## 5. 评审时间线

| 步骤 | 预计耗时 | 产出 |
|------|---------|------|
| Step 1: 自动化扫描 | 15 min | 机器扫描报告 |
| Step 2: 人工评审 | 2 h | 维度评审表（4份计划） |
| Step 3: 修复 | 1-2 h | 修正后的实施计划 |
| Step 4: 复审 | 30 min | 修复确认 |
| Step 5: 出具报告 | 30 min | 正式评审报告 |
| **合计** | **4-5 h** | |

## 6. 评审通过标准

| 条件 | 要求 |
|------|------|
| 无一票否决项 | V1-V5 全部未触发 |
| 总分 >= 85 | A 级以上（每份计划独立判定） |
| P0 问题数 = 0 | 无事实错误 |
| P1 问题修复率 = 100% | 全部遗漏已补齐 |

4份实施计划均需独立达到以上条件。全部通过后，标记为"评审通过"，可进入代码实施阶段。
