## 3. 各维度评审细则

### D1: DOMAIN 领域模型覆盖（12 分）

**检查方法**：逐一比对 `领域模型总览.md` 中定义的 9 个聚合根 + 全部内部实体。

| 检查项 | 来源文档 | 预期映射位置 |
|--------|---------|-------------|
| 9 个聚合根是否在数据库设计中有对应表 | 领域模型总览 §9.3 | 数据库设计 §4 |
| 内部实体（AdverseReaction, PreCheckRecord, HospitalVaccineStock 等）是否映射 | 各上下文文档 | 数据库设计 §4 |
| 值对象（InjectionId, QueueNo 等）是否体现在表设计中 | 各上下文文档 | 数据库设计字段 |
| 18 个领域事件是否在架构设计中说明通信机制 | 领域模型总览 §9.4 | 架构设计 §3.4 |
| 7 个 Repository 接口是否在架构设计中说明实现策略 | 各上下文文档 | 架构设计 §3.5 |

**扣分规则**：每个缺失聚合根 -2 分，每个缺失实体 -1 分，每个缺失事件通信机制 -0.5 分。

### D2: DDL 一致性（12 分）

**检查方法**：逐表比对 DOMAIN 各上下文文档中的 DDL 与数据库设计中的表定义。

| 检查项 | 说明 |
|--------|------|
| 表名一致 | DOMAIN DDL 中的表名 = 数据库设计中的表名 |
| 字段名一致 | DOMAIN DDL 中的列名 = 数据库设计中的字段名 |
| 字段类型一致 | DOMAIN DDL 中的数据类型 = 数据库设计中的数据类型 |
| 约束一致 | PK、UNIQUE、NOT NULL、DEFAULT 约束一致 |
| 索引一致 | DOMAIN DDL 中定义的索引 = 数据库设计中的索引 |
| 表数量一致 | DOMAIN 总计 27 张表 = 数据库设计中实际表数量 |

**扣分规则**：每个字段类型/约束不一致 -0.5 分，每张缺失表 -1 分，每个缺失索引 -0.3 分。

### D3: AppService 覆盖（11 分）

**检查方法**：逐一比对 `应用层设计.md` 中 7 个 AppService 的全部方法与 API 设计中的端点。

| AppService | 方法数 | API 端点对应 |
|-----------|-------|-------------|
| IdentityAppService | 19 | /user/*, /public/auth/* |
| AppointmentAppService | 7 | /user/appointments/* |
| FlowAppService | 5 | /signin/*, /precheck/queue |
| RegisterAppService | 5 | /register/* |
| VaccinateAppService | 4 | /vaccinate/* |
| ObserveAppService | 6 | /observe/*, /precheck/execute |
| StockAppService | 11 | /stock/* |

**扣分规则**：每个缺失的 AppService 方法 -0.5 分，每个新增但无 AppService 对应的端点 -0.3 分（除非合理扩展）。

### D4: 架构↔数据库一致性（10 分）

| 检查项 | 说明 |
|--------|------|
| 数据库类型 = MySQL 8.0 | 架构设计选型 = 数据库设计 |
| 字符集 = utf8mb4 | 架构设计是否提及 |
| 存储引擎 = InnoDB | 数据库设计是否声明 |
| 事务隔离 = READ_COMMITTED | 架构设计原则 vs 数据库设计是否声明 |
| Redis 用途匹配 | 架构设计中 Redis 的 3 个用途（验证码/Token黑名单/排队缓存）是否与数据库设计中隐含的 Redis 使用场景一致 |
| 无物理外键 | 架构设计是否声明 + 数据库设计中是否确实无 FK |

### D5: 架构↔API 一致性（10 分）

| 检查项 | 说明 |
|--------|------|
| Base URL = /api/v1 | 两份文档一致 |
| 认证方式 = JWT Bearer | 架构设计 §5.1 vs API 设计 §1.4 |
| 响应格式 | ApiResponse 结构一致（code/message/data/timestamp） |
| 分页格式 | PageData 结构一致（records/total/page/size/pages） |
| 错误响应策略 | HTTP 200 + business code vs HTTP 401/403/500 |
| API 路由角色映射 | 架构设计中 ApiRoleMapping vs API 设计中的路由前缀表 |
| 防重放机制 | 架构设计提及 vs API 设计 §14 定义 |

### D6: 数据库↔API 一致性（10 分）

**检查方法**：检查 API 请求/响应 DTO 中的字段名是否与数据库表字段对应（驼峰 vs 下划线转换）。

| 检查项 | 说明 |
|--------|------|
| 请求 DTO 字段可映射到数据库字段 | 如 appointmentDate → appointment_date |
| 响应 DTO 字段可从数据库字段组装 | 如 childName ← child_profile.name |
| 枚举值一致 | 如 status 1/2/3/4/6/7/8/9/10 在两份文档中含义一致 |
| 分页参数一致 | page/size 参数在 API 设计和数据库查询中一致 |
| 时间格式一致 | 日期格式（yyyy-MM-dd）在两份文档中一致 |

### D7: 错误码覆盖（7 分）

**检查方法**：比对共享内核中定义的全部 70+ 错误码与 API 设计中引用的错误码。

| 模块 | DOMAIN 错误码数量 | 需确认 API 设计中已引用 |
|------|-----------------|---------------------|
| 系统 (1000-1999) | 12 | UNAUTHORIZED, FORBIDDEN, BAD_REQUEST 等 |
| 预约 (2000-2999) | 9 | APPOINT_CHILD_NOT_FOUND 等 |
| 流程 (3000-3999) | 10 | SIGNIN_STATUS_INVALID 等 |
| 库存 (4000-4999) | 10 | STOCK_BATCH_NOT_FOUND 等 |
| 登记 (5000-5999) | 4 | REGISTER_STATUS_INVALID 等 |
| 接种 (6000-6999) | 10 | VACCINATE_STATUS_INVALID 等 |
| 用户 (7000-7999) | 14 | USER_PHONE_DUPLICATE 等 |
| 管理 (8000-8999) | 14 | ROLE_CODE_DUPLICATE 等 |

**扣分规则**：每个在 DOMAIN 中定义但在 API 设计中未使用的错误码 -0.1 分，每个在 API 中引用但 DOMAIN 中未定义的错误码 -0.2 分。

### D8: 权限码覆盖（7 分）

**检查方法**：比对共享内核中定义的全部 56 个权限码与 API 路由角色映射。

| 检查项 | 说明 |
|--------|------|
| 56 个权限码是否在 API 设计中有对应端点 | 每个权限码至少被一个 API 端点使用 |
| API 路由角色映射是否覆盖 10 个角色 | USER + 7 DOCTOR + BUSINESS_ADMIN + SUPER_ADMIN |
| 公共接口（无需权限）是否正确标记 | /api/v1/public/* 无需认证 |

### D9: 索引设计合理性（7 分）

| 检查项 | 说明 |
|--------|------|
| 预约创建容量检查：idx_date_slot_status | 覆盖 WHERE vaccine_id + date + slot + status |
| 用户预约查询：idx_user_id + idx_status | 覆盖 WHERE user_id + status |
| FEFO 批次选取：idx_vaccine_id + idx_expiry_date | 覆盖 WHERE vaccine_id ORDER BY expiry_date |
| 库存锁定/扣减：uk_hospital_batch | 唯一索引 WHERE batch_id |
| 库存汇总乐观锁：uk_hospital_vaccine + version 字段 | 覆盖 WHERE id AND version |
| 登录查询：uk_phone | 覆盖 WHERE phone |
| 一对一关联查询：uk_appointment_id（register_queue, vaccination_record, pre_check_record, observe_record） | 防重复 + 快速关联查询 |

### D10: 状态机完整性（7 分）

**检查方法**：比对共享内核中的状态转换矩阵与 API 设计中的业务规则。

| 检查项 | 说明 |
|--------|------|
| 9 个状态是否全部定义 | 1/2/3/4/6/7/8/9/10 |
| 8 个合法转换是否在 API 中有对应端点 | 1→3(取消), 1→4(过期), 1→6(签到), 6→7(预检通过), 6→9(预检失败), 7→8(登记), 8→10(接种), 10→2(留观结束) |
| 每个转换的触发角色是否正确 | 与 DOMAIN 中定义的角色一致 |
| 无死状态 | 每个终态（2/3/4/9）无出边，每个中间态（1/6/7/8/10）至少有 1 个出边 |
| 过期转换（1→4）的触发方式 | 定时任务，在 API 设计/架构设计中是否有定时任务覆盖 |

### D11: REQ 功能覆盖（7 分）

**检查方法**：比对 7 个 REQ 模块中定义的功能点与 API 设计中的端点。

| REQ 模块 | 关键功能点 | API 对应 |
|---------|---------|---------|
| REQ-USER | 注册/登录/修改密码/重置密码/冻结解冻/儿童档案CRUD | /user/* |
| REQ-APPOINTMENT | 创建预约/取消预约/预约列表/预约详情 | /user/appointments/* |
| REQ-FLOW | 签到/预检/排队查询/流程指引 | /signin/*, /precheck/* |
| REQ-REGISTER | 登记/核实/批次分配/排队管理 | /register/* |
| REQ-VACCINATE | 接种执行/核实/记录查询 | /vaccinate/* |
| REQ-STOCK | 库存总览/批次管理/调拨/销毁/预警 | /stock/* |
| REQ-ADMIN | 疫苗目录/角色权限/用户管理/窗口/排班/配置/公告/统计 | /admin/* |

## 4. 评审执行步骤

### Step 1: 自动化扫描（约 30 分钟）

扩展现有 `docs/tools/verify_consistency/` 工具，新增 3 个检查器：

| 检查器 | 输入 | 输出 |
|--------|------|------|
| `domain_db_checker.py` | DOMAIN DDL + 数据库设计文档 | 字段类型/约束/索引差异列表 |
| `domain_api_checker.py` | DOMAIN-APP-SERVICE + API 设计文档 | 方法覆盖矩阵 |
| `cross_doc_checker.py` | 架构设计 + 数据库设计 + API 设计 | 三文档交叉引用一致性 |

### Step 2: 人工评审（约 2 小时）

按维度逐项评审，填写评审表：

```
维度 | 满分 | 得分 | 问题列表
D1   | 12   |  ?   | P0: xxx, P1: xxx
D2   | 12   |  ?   |
...
```

问题优先级定义：

| 级别 | 说明 | 处理要求 |
|------|------|---------|
| P0 | 事实错误（字段名/类型不匹配、表缺失） | 必须修复 |
| P1 | 遗漏（缺少索引、缺少端点、缺少错误码） | 必须修复 |
| P2 | 不一致（文档间描述矛盾） | 应当修复 |
| P3 | 优化建议（索引优化、命名改进） | 可选修复 |

### Step 3: 修复（约 1-2 小时）

按 P0 → P1 → P2 → P3 优先级修复。

### Step 4: 复审（约 30 分钟）

验证修复是否正确，确认无引入新问题。

### Step 5: 出具评审报告

```
docs/05-DESIGN/review/
└── 新增文档评审报告.md
```

报告结构：
1. 评分总览（11 维度得分表 + 三支柱汇总）
2. 一票否决项检查结果
3. 各维度详细评审结果（问题列表 + 修复确认）
4. 版本变更记录
5. 最终结论
