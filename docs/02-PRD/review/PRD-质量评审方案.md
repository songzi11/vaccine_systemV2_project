# PRD 质量评审方案（SRD一致性 & 逻辑闭环专项）

> **版本:** V1.0
> **评审日期:** 2026-04-03
> **评审对象:** PRD-ADMIN、PRD-USER、PRD-APPOINTMENT、PRD-FLOW、PRD-REGISTER、PRD-VACCINATE、PRD-STOCK
> **对照基准:** 疫苗管理系统业务规格说明书 V2.6（SRD）
> **评审核心目标:** PRD与SRD完全一致，内部逻辑无矛盾，业务流程完美闭环

---

## 一、评审总览

### 1.1 评审理念

本评审方案围绕三个核心命题展开：

| 核心命题 | 一句话定义 | 评审原则 |
|---------|-----------|---------|
| **SRD一致性** | PRD中的每一个需求都能在SRD中找到出处，SRD中的每一个需求都被PRD完整承接 | 双向追溯、无遗漏、无偏离 |
| **逻辑无矛盾** | PRD内部的规则之间不冲突，PRD之间的规则之间不冲突，PRD与SRD之间不冲突 | 矛盾即零分、一处矛盾扣除全维度 |
| **完美闭环** | 每一个状态有入口和出口，每一条数据有创建和终结，每一个异常有触发和恢复，每一条流程有起点和终点 | 无断链、无悬空、无死路 |

### 1.2 三大支柱与权重分配

```
总分 100 分
├── 支柱一：SRD 一致性（40分）
│   ├── D1  SRD功能需求覆盖率     12分
│   ├── D2  SRD业务规则一致性     12分
│   ├── D3  SRD数据模型一致性      8分
│   └── D4  SRD角色权限一致性      8分
│
├── 支柱二：逻辑无矛盾（30分）
│   ├── D5  PRD内部逻辑自洽性     10分
│   ├── D6  跨模块逻辑一致性      10分
│   └── D7  异常处理逻辑完备性    10分
│
└── 支柱三：完美闭环（30分）
    ├── D8  状态机闭环             10分
    ├── D9  数据生命周期闭环       10分
    └── D10 业务流程闭环           10分
```

### 1.3 评分规则

| 评分段 | 含义 | 判定标准 |
|--------|------|---------|
| 90%-100% | 完美 | 零缺陷，或仅有轻微措辞问题 |
| 75%-89% | 良好 | 存在少量不一致/小缺陷，但不影响整体正确性 |
| 60%-74% | 合格 | 存在明显不一致或闭环缺失，但核心逻辑成立 |
| 40%-59% | 不合格 | 存在逻辑矛盾或严重闭环断裂，需大幅修改 |
| 0%-39% | 严重缺陷 | 存在多处矛盾/大面积闭环缺失，需重写 |

### 1.4 一票否决项（发现任一则对应支柱直接0分）

| 编号 | 否决项 | 所属支柱 |
|------|--------|---------|
| V1 | SRD中定义的功能模块在PRD中完全缺失 | 支柱一 |
| V2 | PRD中定义的业务规则与SRD直接矛盾 | 支柱一 |
| V3 | 同一PRD内部存在两条互相矛盾的规则 | 支柱二 |
| V4 | 两个PRD对同一实体/字段/状态的定义互相矛盾 | 支柱二 |
| V5 | 核心业务流程（预约→签到→预检→登记→接种→留观）存在不可达的环节 | 支柱三 |

## 二、支柱一：SRD 一致性（40分）

### D1 — SRD功能需求覆盖率（12分）

**评审目标：** SRD中声明的每一个功能需求，都被PRD完整承接，无遗漏、无多余。

#### 检查方法

**Step 1：正向覆盖检查（SRD → PRD）**

逐条核对SRD第2.2节"功能模块"中列出的功能点，在PRD中找到对应的功能定义。

| SRD功能模块 | SRD功能点 | 对应PRD | 覆盖状态 |
|------------|----------|---------|---------|
| 用户管理 | 用户注册、登录、角色分配、权限管理 | PRD-USER | ☐ |
| 窗口管理 | 窗口配置、职能定义、容量调整、服务描述 | PRD-ADMIN | ☐ |
| 医生排班 | 排班创建、修改、查询、医生调度 | PRD-ADMIN | ☐ |
| 疫苗管理 | 疫苗目录、批次管理、FEFO分配 | PRD-ADMIN | ☐ |
| 库存管理 | 库存查询、调拨、销毁、预警 | PRD-STOCK | ☐ |
| 用户预约 | 线上预约、取消预约、预约查询 | PRD-APPOINTMENT | ☐ |
| 签到管理 | 身份核实、预约确认、窗口分配 | PRD-FLOW | ☐ |
| 预检管理 | 健康评估、禁忌筛查、预检报告 | PRD-FLOW | ☐ |
| 登记管理 | 信息核实、批次分配、排队管理 | PRD-REGISTER | ☐ |
| 接种管理 | 接种执行、记录登记、库存扣减 | PRD-VACCINATE | ☐ |
| 留观管理 | 留观监测、不良反应处理、结束确认 | PRD-FLOW | ☐ |
| 公告管理 | 公告发布、审批、查看、反馈 | PRD-ADMIN + PRD-USER | ☐ |
| 统计分析 | 接种统计、库存统计、效率统计 | PRD-ADMIN | ☐ |

**Step 2：反向多余检查（PRD → SRD）**

逐条核对每个PRD的功能清单，确认每个功能都能追溯到SRD中的需求来源。PRD中不得出现SRD未定义的功能（除非有明确标注为"PRD扩展"并说明原因）。

**Step 3：统计覆盖度**

```
覆盖率 = (SRD功能点被PRD覆盖的数量) / (SRD功能点总数) × 100%
```

#### 评分标准

| 分数段 | 标准 |
|--------|------|
| 12 | 覆盖率100%，无多余功能 |
| 10-11 | 覆盖率100%，存在1-2个PRD扩展功能（已标注原因） |
| 8-9 | 覆盖率≥95%，缺失1-2个SRD功能点 |
| 5-7 | 覆盖率≥85%，缺失3-5个SRD功能点 |
| 0-4 | 覆盖率<85%，或触发一票否决V1 |

### D2 — SRD业务规则一致性（12分）

**评审目标：** PRD中的每一条业务规则，与SRD中的定义完全一致，不得偏离、不得简化、不得矛盾。

#### 检查方法

**Step 1：规则提取与映射**

从SRD中提取所有业务规则，按模块分类后与PRD逐条对照。

需检查的SRD规则来源：
- SRD第5节"核心业务流程"中的所有流程规则
- SRD第7节"库存管理体系"中的所有库存规则
- SRD第8节"数据模型设计"中的所有约束规则
- SRD第10节"异常处理规则"中的所有异常规则
- SRD第3节"用户角色与权限"中的所有权限规则
- SRD第4节"窗口管理体系"中的所有窗口规则

**Step 2：规则一致性判定**

对每条规则，判定一致性等级：

| 一致性等级 | 定义 | 示例 |
|-----------|------|------|
| 一致 | PRD规则与SRD完全相同 | SRD: "预约时段30分钟粒度" → PRD: "预约时段30分钟粒度" |
| 等价表述 | PRD用不同措辞但语义完全相同 | SRD: "先过期先出" → PRD: "FEFO（First Expired First Out）" |
| 细化扩展 | PRD在SRD基础上增加了可执行的细节 | SRD: "预约后系统发送通知" → PRD: "预约成功后推送APP站内消息，包含预约时间、窗口信息" |
| **偏离** | PRD规则与SRD不一致 | SRD: "爽约3次冻结30天" → PRD: "爽约3次冻结15天" |
| **矛盾** | PRD规则与SRD直接冲突 | SRD: "接种完成后开始留观计时" → PRD: "登记完成后开始留观计时" |

**Step 3：偏离和矛盾的严重性分级**

| 严重性 | 定义 | 扣分 |
|--------|------|------|
| 严重矛盾 | 规则含义直接冲突，导致业务行为不同 | -4分/处 |
| 偏离 | 规则方向一致但具体数值/条件不同 | -2分/处 |
| 简化遗漏 | SRD有规则但PRD未提及 | -1分/处 |

#### 评分标准

| 分数段 | 标准 |
|--------|------|
| 12 | 所有规则一致或等价表述，无偏离、无矛盾 |
| 10-11 | 存在细化扩展，无偏离、无矛盾 |
| 7-9 | 存在1-2处简化遗漏（-1/处），无偏离无矛盾 |
| 4-6 | 存在1处偏离（-2），或3-4处简化遗漏 |
| 0-3 | 存在严重矛盾（触发V2），或≥2处偏离，或大面积简化遗漏 |

### D3 — SRD数据模型一致性（8分）

**评审目标：** PRD中的数据实体、字段定义、约束条件与SRD完全一致。

#### 检查方法

**Step 1：实体覆盖检查**

将SRD第8节"数据模型设计"中的所有实体（数据表）与PRD第6节"字段设计"中的实体交叉对照：

| 检查项 | 说明 |
|--------|------|
| 实体完整性 | SRD中每个表在PRD中都有定义 |
| 字段完整性 | SRD中每个字段在PRD中都有定义 |
| 字段类型一致 | 数据类型（varchar/int/datetime等）完全一致 |
| 字段长度一致 | varchar长度、int精度完全一致 |
| 必填标志一致 | NOT NULL / NULL定义完全一致 |
| 默认值一致 | DEFAULT值完全一致 |
| 枚举值一致 | 枚举类型的取值范围完全一致 |
| 主键/外键一致 | 主键定义和外键关联完全一致 |

**Step 2：跨PRD数据模型一致性**

对于被多个PRD引用的共享实体/字段，验证定义是否完全一致：

| 共享实体 | 涉及PRD | 需一致性验证 |
|---------|---------|-------------|
| appointment表 | APPOINTMENT, FLOW, REGISTER, VACCINATE | 字段类型、长度、枚举值 |
| pre_check_record表 | APPOINTMENT, FLOW | 字段类型、长度、默认值 |
| register_queue表 | APPOINTMENT, REGISTER | 字段类型、长度、默认值 |
| observe_record表 | APPOINTMENT, FLOW | 字段类型、长度、必填标志 |
| vaccination_record表 | APPOINTMENT, VACCINATE, USER, ADMIN | 字段类型、长度 |
| child_profile表 | USER, APPOINTMENT, VACCINATE, ADMIN | 字段类型、长度 |
| vaccine_batch表 | STOCK, REGISTER, ADMIN | 字段类型、长度、枚举值 |

#### 评分标准

| 分数段 | 标准 |
|--------|------|
| 8 | 所有实体和字段与SRD完全一致，跨PRD共享实体零差异 |
| 6-7 | 跨PRD共享实体存在1-2处细微差异（如长度取大值），已统一 |
| 4-5 | 跨PRD共享实体存在3-5处差异，或SRD实体有1-2个字段在PRD中缺失 |
| 2-3 | 跨PRD共享实体存在≥6处差异，或存在类型/枚举不一致 |
| 0-1 | 存在关键字段矛盾（如必填标志相反、枚举值不同），或SRD实体在PRD中完全缺失 |

**评审目标：** PRD中的角色定义、权限分配与SRD第3节完全一致。

**Step 1：角色清单对照**

| 检查项 | 说明 |
|--------|------|

| 角色编码 | 角色编码是否与SRD一致（如SUPER_ADMIN而非SystemAdmin） |
| 角色职责 | 角色职责描述是否与SRD一致 |
| 角色数量统计 | 各角色权限数量是否与SRD 3.3节统计一致 |

**Step 2：权限清单逐条对照**

对每个角色，逐条核对权限编码和权限名称：

| 角色 | SRD权限数 | PRD权限数 | 逐条对照 |
|------|----------|----------|---------|
| SUPER_ADMIN | 7 | ☐ | ☐ |
| DOCTOR_BUSINESS_ADMIN | 7 | ☐ | ☐ |
| DOCTOR_SCHEDULE | 5 | ☐ | ☐ |
| DOCTOR_SIGNIN | 4 | ☐ | ☐ |
| DOCTOR_PRECHECK | 5 | ☐ | ☐ |
| DOCTOR_REGISTER | 5 | ☐ | ☐ |
| DOCTOR_VACCINATE | 6 | ☐ | ☐ |
| DOCTOR_STOCK | 6 | ☐ | ☐ |
| DOCTOR_OBSERVE | 6 | ☐ | ☐ |
| USER | 9 | ☐ | ☐ |

**Step 3：权限隔离规则验证**

核对SRD中声明的特殊权限隔离规则在PRD中是否被正确实现：
- DOCTOR_VACCINATE 只能查看自己的接种记录
- SUPER_ADMIN 不可被修改/冻结
- 用户只能操作自己的儿童档案
- 医生只能在自己排班的窗口工作

#### 评分标准

| 分数段 | 标准 |
|--------|------|
| 8 | 10种角色、48个权限完全一致，权限隔离规则全部正确实现 |
| 6-7 | 权限编码/名称有1-2处不一致，或1条隔离规则未在PRD中体现 |
| 4-5 | 角色权限数量有差异，或2-3条权限在PRD中缺失 |
| 2-3 | 权限隔离规则被违反（如PRD允许医生查看他人记录），或角色编码不一致 |
| 0-1 | 角色定义与SRD直接矛盾，或大面积权限缺失 |

## 三、支柱二：逻辑无矛盾（30分）

### D5 — PRD内部逻辑自洽性（10分）

**评审目标：** 单个PRD文档内部的所有规则、约束、流程之间不存在自相矛盾。

#### 检查方法

对每个PRD，执行以下自洽性检查：

**检查1：功能规则自洽**

对PRD第5节"业务规则"中的所有规则，两两检查是否存在矛盾：

```
检查矩阵：对规则 Ri 和 Rj (i < j)：
- 如果 Ri 和 Rj 描述同一场景但结论不同 → 矛盾
- 如果 Ri 的前提条件与 Rj 的结论冲突 → 矛盾
- 如果 Ri 允许某操作但 Rj 禁止同一操作 → 矛盾
```

**检查2：功能与字段约束自洽**

检查功能描述中的业务约束与字段定义中的约束是否一致：
- 功能说"必填"但字段定义为NULL → 矛盾
- 功能说"长度限制20字"但字段定义为varchar(50) → 不一致
- 功能说"取值为A/B/C"但字段枚举定义包含D → 不一致

**检查3：正常流程与异常场景自洽**

检查异常场景是否与正常流程矛盾：
- 正常流程要求步骤A必须在步骤B之前，但异常处理允许跳过A → 矛盾
- 功能定义说"系统自动处理"，但异常场景说"需要手动处理" → 需确认是否有条件分支

**检查4：API设计与功能描述自洽**

- 功能描述的操作与API的HTTP方法是否匹配（查询用GET，创建用POST等）
- API的输入参数是否覆盖功能描述的所有输入
- API的响应是否覆盖功能描述的所有输出

#### 评分标准

| 分数段 | 标准 |
|--------|------|
| 10 | 四项检查全部通过，零矛盾 |
| 7-9 | 存在1-2处轻微不一致（如字段长度余量不同），但不影响业务逻辑 |
| 4-6 | 存在1处逻辑矛盾（触发V3判定），或3-5处不一致 |
| 0-3 | 存在≥2处逻辑矛盾，或大面积不一致 |

### D6 — 跨模块逻辑一致性（10分）

**评审目标：** 多个PRD之间对共享概念、共享实体、共享流程的定义完全一致，不存在跨模块矛盾。

#### 检查方法

**检查1：共享实体定义一致性**

对以下跨模块引用的实体，验证所有PRD的定义完全一致：

| 实体 | 需验证的字段 | 涉及PRD |
|------|-------------|---------|
| appointment | status枚举值、状态流转规则 | APPOINTMENT, FLOW, REGISTER, VACCINATE |
| pre_check_record | 字段类型、长度、必填标志 | APPOINTMENT, FLOW |
| register_queue | 字段类型、长度、默认值 | APPOINTMENT, REGISTER |
| observe_record | 字段类型、长度、必填标志 | APPOINTMENT, FLOW |
| vaccination_record | 字段类型、长度 | APPOINTMENT, VACCINATE, USER, ADMIN |
| child_profile | 字段类型、长度 | USER, APPOINTMENT, VACCINATE, ADMIN |
| vaccine_batch | status枚举、字段类型 | STOCK, REGISTER, ADMIN |
| sys_user | status枚举、冻结规则 | USER, APPOINTMENT |

**检查2：跨模块流程衔接一致性**

验证相邻模块之间的流程衔接是否存在矛盾：

| 衔接点 | 模块A的输出 | 模块B的输入 | 需验证 |
|--------|-----------|-----------|--------|
| 预约→签到 | APPOINTMENT创建的预约记录 | FLOW执行签到 | 状态值、数据完整性 |
| 签到→预检 | FLOW签到完成 | FLOW预检开始 | 状态流转条件 |
| 预检→登记 | FLOW预检通过 | REGISTER开始登记 | 预检结果传递 |
| 登记→接种 | REGISTER批次分配完成 | VACCINATE执行接种 | 库存锁定状态 |
| 接种→留观 | VACCINATE接种完成 | FLOW开始留观 | 触发条件、计时起点 |
| 接种→库存 | VACCINATE接种消耗 | STOCK库存扣减 | 扣减逻辑、数量计算 |

**检查3：错误码全局唯一性**

验证所有PRD使用的错误码全局唯一，不存在跨模块冲突：

```
检查方法：汇总所有PRD的异常场景错误码，检查是否有重复。
对每个错误码：错误码 → (所属模块, 业务场景) 应为一一映射。
```

**检查4：术语一致性**

验证同一概念在所有PRD中使用统一术语：

| 概念 | 统一术语 | 禁止使用 |
|------|---------|---------|
| 用户状态 | 已冻结/已禁用 | 二者不得混用 |
| 家长 | 用户 | 不得用"家长"和"用户"指代同一角色 |
| 预约状态 | PENDING/SIGNED_IN/PRECHECKED/... | 枚举值不得有差异 |
| 疫苗类别 | 一类疫苗/二类疫苗（存储值CLASS_I/CLASS_II） | 不得混用中英文 |

#### 评分标准

| 分数段 | 标准 |
|--------|------|
| 10 | 四项检查全部通过，零跨模块矛盾 |
| 7-9 | 存在1-2处术语不一致或字段细微差异，已统一 |
| 4-6 | 存在1处跨模块实体矛盾（触发V4），或错误码冲突 |
| 0-3 | 存在≥2处跨模块矛盾，或流程衔接存在断裂 |

### D7 — 异常处理逻辑完备性（10分）

**评审目标：** 每个功能的每个异常场景都有明确的触发条件、错误码、错误消息、用户可见提示和处理策略，且异常处理逻辑本身不产生矛盾。

#### 检查方法

**检查1：异常场景穷举性**

对每个功能，枚举所有可能的异常场景并检查PRD是否覆盖：

| 异常类型 | 检查要点 |
|---------|---------|
| 输入校验异常 | 必填字段为空、格式错误、长度超限、类型错误 |
| 业务规则异常 | 状态不允许、条件不满足、数量超限、时间窗口不匹配 |
| 权限异常 | 未登录、角色无权限、数据不属于当前用户 |
| 并发异常 | 重复操作、并发修改、资源竞争 |
| 依赖异常 | 关联数据不存在、关联服务不可用 |
| 系统异常 | 数据库异常、网络超时、磁盘空间不足 |

**检查2：异常处理逻辑无矛盾**

- 同一错误码不得对应两种不同的处理策略
- 异常A的处理策略不得与异常B的处理策略冲突
- 异常恢复后的状态不得违反业务规则

**检查3：错误码体系完整性**

- 错误码是否按SRD第10节的分段规则分配
- 错误码是否全局唯一（D6已检查）
- 错误消息是否清晰可读，能指导用户操作
- 前端是否能根据错误码做出正确的UI响应

#### 评分标准

| 分数段 | 标准 |
|--------|------|
| 10 | 异常场景完整覆盖6种类型，处理逻辑无矛盾，错误码体系规范 |
| 7-9 | 覆盖5种类型，或存在1-2个功能的异常场景有遗漏 |
| 4-6 | 覆盖3-4种类型，或存在1处异常处理逻辑矛盾 |
| 0-3 | 仅覆盖输入校验和业务规则2种类型，或存在多处异常处理矛盾 |

## 四、支柱三：完美闭环（30分）

### D8 — 状态机闭环（10分）

**评审目标：** 每个核心实体的状态机是一个完整的闭环：每个状态都有明确的进入条件和退出条件，没有悬空状态（只能进不能出）、没有死路状态（只能出不能进）、没有孤立状态（无法到达）。

#### 检查方法

**Step 1：提取所有状态机**

从PRD中提取所有有状态流转的实体：

| 实体 | 所属PRD | 状态集合 |
|------|---------|---------|
| appointment | APPOINTMENT | ☐ 提取所有状态值 |
| pre_check_record | FLOW | ☐ |
| register_queue | REGISTER | ☐ |
| vaccination_record | VACCINATE | ☐ |
| observe_record | FLOW | ☐ |
| vaccine_batch | STOCK | ☐ |
| sys_user | USER | ☐ |
| announcement | ADMIN | ☐ |

**Step 2：闭环四项验证**

对每个状态机，执行以下四项验证：

```
验证1 — 入口验证：每个非初始状态，是否至少有一个合法的前置状态可以转入？
  → 如果状态S没有合法的转入路径，则S是"孤立状态"（死路）

验证2 — 出口验证：每个非终态，是否至少有一个合法的转出路径？
  → 如果状态S没有合法的转出路径且不是终态，则S是"悬空状态"（陷阱）

验证3 — 初始状态验证：是否有且仅有一个明确的初始状态？
  → 如果没有初始状态或有多于一个初始状态，状态机不完整

验证4 — 终态验证：每个业务流程是否都有明确的终态？
  → 正常流程终态（成功完成）
  → 异常流程终态（取消、失败、超时）
  → 终态不得有转出路径（否则不是终态）
```

**Step 3：流转条件完备性**

对每条状态流转边，验证：
- 触发条件是否明确（什么操作/什么事件触发）
- 前置条件是否完整（需要满足什么前置条件）
- 后置效果是否明确（状态变更后产生什么副作用）
- 是否存在条件冲突（同一条件下可以转到两个不同状态）

#### 评分标准

| 分数段 | 标准 |
|--------|------|
| 10 | 所有状态机通过四项验证，流转条件完备，零孤立/悬空状态 |
| 7-9 | 1个状态机存在1个孤立/悬空状态（非核心实体），或1条流转边条件不完整 |
| 4-6 | 1个核心实体状态机存在孤立/悬空状态，或2-3个非核心实体有问题 |
| 0-3 | 核心业务流程状态机（appointment）存在断裂，或多个状态机有问题 |

### D9 — 数据生命周期闭环（10分）

**评审目标：** 每一条业务数据从创建到终结都有完整的生命周期管理，不存在"创建了但永远不处理"、"处理了但没有结果记录"、"终结了但关联数据未清理"等情况。

#### 检查方法

**检查1：数据创建闭环**

| 检查项 | 说明 |
|--------|------|
| 创建者明确 | 每条记录的创建操作是否由明确的功能触发 |
| 创建时机合理 | 数据创建的时机是否符合业务流程顺序 |
| 创建完整性 | 创建记录时是否填充了所有必填字段 |

**检查2：数据流转闭环**

| 检查项 | 说明 |
|--------|------|
| 读写对称 | 被某个模块写入的数据，是否被后续模块正确读取和使用 |
| 传递完整性 | 模块间传递数据时，是否有字段丢失或变形 |
| 更新原子性 | 跨模块的数据更新是否保证原子性（事务边界是否明确） |

**检查3：数据终结闭环**

| 检查项 | 说明 |
|--------|------|
| 终结条件明确 | 每种数据是否有明确的终结条件（成功完成、取消、过期、删除） |
| 终结后处理 | 数据终结后，关联数据是否被正确处理（级联更新/删除/归档） |
| 资源释放 | 数据终结后，占用的资源是否被释放（如预约取消后释放时段名额、库存锁定释放） |

**检查4：特定数据生命周期追踪**

| 数据 | 创建 | 流转 | 终结 | 需验证 |
|------|------|------|------|--------|
| 预约记录 | 创建预约 | 签到→预检→登记→接种→留观 | 完成/取消/过期 | 取消后是否释放名额？过期后是否释放资源？ |
| 库存锁定 | 登记时锁定 | 接种时确认扣减 | 接种完成释放 | 锁定超时是否自动释放？ |
| 留观记录 | 接种完成创建 | 留观计时 | 留观结束/不良反应 | 异常中断后留观记录如何处理？ |
| 排队记录 | 签到时入队 | 各窗口流转 | 接种完成出队 | 用户中途离开队列如何处理？ |

#### 评分标准

| 分数段 | 标准 |
|--------|------|
| 10 | 四项检查全部通过，所有数据生命周期完整闭环 |
| 7-9 | 1-2条数据的终结处理不够明确（如"由系统处理"但未说明具体逻辑） |
| 4-6 | 1条核心数据存在生命周期断裂（如资源未释放），或3-5条数据终结不明确 |
| 0-3 | 多条核心数据生命周期断裂，或存在资源泄漏风险 |

### D10 — 业务流程闭环（10分）

**评审目标：** 核心业务流程从起点到终点是一条完整的闭环链路，没有断链（中间环节缺失）、没有旁路（绕过某个必要环节）、没有死路（流程进行到某步无法继续）。

#### 检查方法

**检查1：主流程完整性（正向链路）**

验证核心业务主流程的每一步都有明确的输入、处理和输出：

```
主流程链路：
用户注册/登录 → 创建预约 → 到院签到 → 预检评估 → 登记核实 → 执行接种 → 留观观察 → 流程结束

对每一步验证：
  ☐ 输入：从上一步接收什么数据？
  ☐ 处理：执行什么操作？
  ☐ 输出：产生什么数据传递给下一步？
  ☐ 异常：如果这一步失败，如何处理？（回退？终止？重试？）
```

**检查2：异常分支闭环（逆向链路）**

验证每个异常分支都有明确的终态：

| 异常场景 | 当前处理 | 是否闭环 | 需验证 |
|---------|---------|---------|--------|
| 预约创建失败 | 返回错误信息 | ☐ | 用户能否修正后重试？ |
| 签到时预约不存在 | 返回错误 | ☐ | 是否需要用户重新预约？ |
| 预检发现禁忌症 | 终止流程 | ☐ | 预约状态如何变更？已锁定库存如何释放？ |
| 登记时库存不足 | 终止流程 | ☐ | 用户如何得知？是否需要重新预约？ |
| 接种时发生不良反应 | 上报并进入观察 | ☐ | 留观流程如何衔接？ |
| 留观发现异常 | 转医疗处理 | ☐ | 接种记录状态如何标记？ |
| 预约取消 | 释放资源 | ☐ | 取消后已进行的步骤（如已签到）如何回滚？ |
| 预约过期 | 自动取消 | ☐ | 过期前是否有提醒？过期后资源是否释放？ |

**检查3：跨模块流程衔接闭环**

验证相邻模块之间的衔接点是否存在断链：

| 衔接点 | 模块A输出 | 模块B输入 | 数据是否完整传递？ |
|--------|----------|----------|-----------------|
| 预约→签到 | appointment记录 | 签到查询预约 | ☐ |
| 签到→预检 | 签到完成状态 | 预检查询待预检队列 | ☐ |
| 预检→登记 | 预检通过状态+预检结果 | 登记查询待登记队列 | ☐ |
| 登记→接种 | 批次分配完成+锁定库存 | 接种查询待接种队列 | ☐ |
| 接种→留观 | 接种完成+留观开始 | 留观查询留观队列 | ☐ |
| 留观→结束 | 留观完成 | 流程结束 | ☐ |

**检查4：反向流程闭环**

验证是否存在需要回退的场景，以及回退逻辑是否完整：

| 回退场景 | 是否定义 | 回退逻辑是否完整 |
|---------|---------|---------------|
| 预检未通过 → 回退到预约状态 | ☐ | ☐ |
| 登记时库存不足 → 回退到预检状态 | ☐ | ☐ |
| 接种失败 → 回退到登记状态 | ☐ | ☐ |
| 留观异常 → 中断并标记 | ☐ | ☐ |
| 用户取消预约（已签到后） | ☐ | ☐ |

#### 评分标准

| 分数段 | 标准 |
|--------|------|
| 10 | 主流程完整，所有异常分支闭环，跨模块衔接无断链，反向流程有定义 |
| 7-9 | 1-2个异常分支闭环不够明确，或1个反向流程未定义 |
| 4-6 | 1个跨模块衔接点存在断链（触发V5判定），或3-5个异常分支未闭环 |
| 0-3 | 主流程存在不可达环节，或多个衔接点断链 |

## 五、评审执行流程

### 5.1 评审准备

1. 确认SRD为最新版本（V2.6）
2. 确认所有PRD为最新版本（V2.0）
3. 准备评审检查表（本文档的检查矩阵）
4. 确定评审人员/Agent分工

### 5.2 评审执行

```
阶段一：支柱一评审（SRD一致性）
  └── 对每个PRD，执行D1-D4的检查方法
  └── 输出：SRD一致性检查清单（逐条对照结果）

阶段二：支柱二评审（逻辑无矛盾）
  └── 对每个PRD，执行D5的内部自洽检查
  └── 对每对相关PRD，执行D6的跨模块检查
  └── 对每个PRD，执行D7的异常处理检查
  └── 输出：矛盾清单（含严重性分级）

阶段三：支柱三评审（完美闭环）
  └── 提取所有状态机，执行D8验证
  └── 追踪所有数据生命周期，执行D9验证
  └── 走查主流程+异常分支+反向流程，执行D10验证
  └── 输出：闭环断裂清单

阶段四：汇总评分
  └── 汇总各维度得分
  └── 检查一票否决项
  └── 计算总分和等级
  └── 生成评审报告
```

### 5.3 评审输出

| 输出物 | 内容 |
|--------|------|
| 各维度评分表 | 10个维度各自的得分、扣分明细、具体问题 |
| 一票否决检查结果 | V1-V5的检查结论 |
| 问题清单 | 按严重性分级的全部问题列表 |
| 闭环断裂清单 | 所有发现的闭环断裂点 |
| 综合评审报告 | 总分、等级、优先改进建议 |

### 5.4 评分等级

| 等级 | 总分范围 | 含义 | 后续动作 |
|------|---------|------|---------|
| S（卓越） | 95-100 | PRD与SRD完美一致，逻辑零矛盾，完美闭环 | 可直接进入开发 |
| A（优秀） | 85-94 | 高度一致，极少量轻微问题 | 修复轻微问题后进入开发 |
| B（良好） | 75-84 | 整体一致，少量不一致/闭环缺口 | 修复后进入开发 |
| C（合格） | 60-74 | 基本一致，存在明显问题 | 需要较多修复 |
| D（不合格） | 40-59 | 存在矛盾或断裂 | 需要大幅修改 |
| F（严重缺陷） | <40 | 存在一票否决项或大面积问题 | 需要重写 |
