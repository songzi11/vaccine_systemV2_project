## 1. 共享内核概述

Shared Kernel 是所有限界上下文共享的代码包，**不是一个独立的限界上下文**。

### 1.1 包含内容

| 类别 | 内容 |
|------|------|
| 枚举定义 | AppointmentStatus, BatchStatus, UserStatus, Gender 等 |
| 常量定义 | 错误码常量、权限编码常量 |
| 基础类 | BaseEntity, BusinessException, ApiResponse |
| 工具类 | 状态机校验、日期计算 |

### 1.2 变更规则

- Shared Kernel 的变更影响**所有上下文**，需协调修改
- 新增枚举值：向后兼容，不影响已有逻辑
- 修改已有枚举值：必须评估所有使用方
- 新增错误码：在对应段范围内新增，不影响已有编码

### 2.3 状态分组

```java
public class AppointmentStatusMachine {
    public static final List<Integer> IN_PROGRESS = List.of(1, 6, 7, 8, 10);
    public static final List<Integer> NORMAL_TERMINAL = List.of(2);
    public static final List<Integer> ABNORMAL_TERMINAL = List.of(3, 4, 9);
    public static final List<Integer> ALL_TERMINAL = List.of(2, 3, 4, 9);

    public static boolean isTerminal(int status) {
        return ALL_TERMINAL.contains(status);
    }

    public static boolean isInProgress(int status) {
        return IN_PROGRESS.contains(status);
    }

    public static void validateTransition(int current, int target) {
        Map<Integer, List<Integer>> TRANSITIONS = Map.of(
            6, List.of(1), 7, List.of(6), 9, List.of(6),
            8, List.of(7), 10, List.of(8), 2, List.of(10),
            3, List.of(1), 4, List.of(1)
        );
        List<Integer> allowed = TRANSITIONS.get(target);
        if (allowed == null || !allowed.contains(current)) {
            throw new BusinessException(1010, "状态流转不允许："
                + current + " → " + target);
        }
    }
}
```

## 4. 统一返回结构

```java
public class ApiResponse<T> {
    private int code;       // 200=成功，其他=失败
    private String message;
    private T data;
    private long timestamp;

    public static <T> ApiResponse<T> success(T data) {
        return new ApiResponse<>(200, "操作成功", data, System.currentTimeMillis());
    }

    public static <T> ApiResponse<T> error(int code, String message) {
        return new ApiResponse<>(code, message, null, System.currentTimeMillis());
    }
}

public class PageData<T> {
    private List<T> records;
    private long total;
    private int page;
    private int size;
    private int pages;
}
```

| 场景 | HTTP | code | 说明 |
|------|------|------|------|
| 正常成功 | 200 | 200 | data 为业务数据 |
| 业务规则失败 | 200 | 非200 | 前端根据 code 处理 |
| 未认证 | 401 | 1001 | Token 无效 |
| 参数格式错误 | 400 | 1003 | @Valid 校验不通过 |
| 系统异常 | 500 | 1007 | 全局兜底 |

## 7. 物理外键策略

> **设计决策：所有 DDL 不使用物理 FOREIGN KEY 约束。**

| 项目 | 说明 |
|------|------|
| 原因 | 高并发场景下外键锁增加事务开销；跨上下文表分属不同限界上下文，物理外键引入不必要的耦合 |
| 替代方案 | 应用层通过 Repository 校验关联数据存在性（如插入前 SELECT 检查） |
| 一致性保障 | 关联数据的完整性由应用层事务和业务逻辑保证 |
| DDL 约定 | 使用 COMMENT 注释标注逻辑 FK 关系（如 `FK → sys_user.id`），便于开发者理解 |

## 9. 并发控制策略

### 9.1 SELECT FOR UPDATE

所有涉及库存变更和状态变更的操作必须在事务内使用行锁。

### 9.2 库存不变量

```
1. available_stock >= 0
2. locked_stock >= 0
3. locked_stock <= available_stock（锁定量不得超过可用量）
4. 可预约量 = available_stock - locked_stock
```

### 9.3 死锁预防

固定加锁顺序：**appointment → vaccine_batch → hospital_vaccine_stock**

> 说明：所有涉及预约状态变更的事务（T3/T4/T5/T6/T7）必须先锁定 appointment 行，
> 再锁定 vaccine_batch / hospital_vaccine_stock。库存内部事务（T8/T9）不涉及 appointment，
> 按 vaccine_batch → hospital_vaccine_stock 顺序加锁。由于没有事务在锁定 batch/stock 之后
> 再去锁 appointment，因此不存在环路死锁。

### 9.4 乐观锁

`hospital_vaccine_summary` 使用 `version` 字段乐观锁。

### 9.5 重试策略

| 操作 | 最大重试 | 间隔 | 策略 |
|------|---------|------|------|
| FEFO批次分配 | 3 | 100ms, 200ms, 400ms | 指数退避 |
| 库存扣减 | 3 | 100ms, 200ms, 400ms | 指数退避 |
| 注射号生成 | 3 | 即时 | 立即重试 |
| 预约创建 | 1 | 即时 | 不重试 |

| 爽约判定 | cancel_time >= appointment_date | 同日或之后取消 |
| 批次FEFO条件 | status = 0, available_stock > locked_stock, expiry_date > NOW() | ORDER BY expiry_date ASC |
| 临期标记 | expiry_date - warning_days < NOW() | status → 1 |
| 过期标记 | expiry_date < NOW() | status → 2 |
| 批次过期扫描 | 每小时 | 定时任务 |
| 库存预警扫描 | 每小时 | 定时任务 |
| 汇总补偿更新 | 每5分钟 | 定时任务 |
| 事务超时 | 30秒 | 单事务最长 |
